**Each of the 5 sections follows the THREE-PART structure from PATTERNS.md (lines 121-163) per D-08:**

### Section 1: `## SRP -- Single Responsibility Principle`
- **Aplicacion correcta:** Definition (2-4 sentences: "Una clase debe tener una sola razon para cambiar"). Business domain example: `OrderProcessor` that ONLY processes orders, with separate `OrderValidator` and `OrderNotifier` classes. Show the code BEFORE (one god class) and AFTER (separated responsibilities).
- **Challenge 1** (business domain — payment system per D-05): Given a `PaymentService` class that validates, charges, logs, and sends receipts, student refactors to separate responsibilities. Pattern 1 collapsible solution with "Puntos clave" bullets.
- **Cuando va demasiado lejos** (per D-09): Anemic domain model anti-pattern. Show an `Order` entity with ONLY properties and ALL logic in `OrderService`, `OrderValidator`, `OrderCalculator` etc. Explain: this is accidental when it results from blindly splitting, but INTENTIONAL in CQRS/event-sourcing architectures.
- Blockquote: `> **Respuesta de entrevista:** "No aplicaria SRP cuando la separacion crea clases anemicas sin comportamiento propio y fuerza a los consumidores a orquestar multiples servicios para una operacion atomica. En CQRS es intencional, en apps CRUD tradicionales suele ser accidental."`

### Section 2: `## OCP -- Open/Closed Principle`
- **Aplicacion correcta:** Definition ("Abierto a extension, cerrado a modificacion"). Business domain: discount calculator using strategy pattern — add new discount types without modifying existing code. Show `IDiscountStrategy` with `PercentageDiscount`, `FixedDiscount`, and how to add `BuyOneGetOneDiscount` without touching existing classes.
- **Challenge 2** (business domain — notifications per D-05): Given a `NotificationSender` with a big if/else for Email/SMS/Push, student refactors to OCP-compliant design using polymorphism. Pattern 1 collapsible solution.
- **Cuando va demasiado lejos** (per D-09): Abstraction overkill — creating an interface for a class that will NEVER have a second implementation. Show a `IDateTimeProvider` wrapping `DateTime.UtcNow` in a simple script/utility that will never need mocking. Note: in testable production code this IS valid, but in a 50-line console tool it's over-engineering.
- Blockquote: `> **Respuesta de entrevista:** "No aplicaria OCP cuando el codigo no tiene una historia real de cambio. Crear abstracciones para extension futura que nunca llega viola YAGNI y anade indirection sin beneficio."`

### Section 3: `## LSP -- Liskov Substitution Principle`
- **Aplicacion correcta:** Definition ("Los subtipos deben ser sustituibles por sus tipos base sin alterar el comportamiento correcto del programa"). Use the RESEARCH.md LSP violation example (lines 255-273): `ReadOnlyCache<T>` implementing `IReadWriteRepository<T>` and throwing `NotImplementedException`. Show the fix: segregate into `IReadRepository<T>` and `IWriteRepository<T>`.
- **Challenge 3** (abstract/technical per D-05 mix): Given a `Bird` base class with `Fly()`, student must fix the `Penguin : Bird` problem (classic). But frame it in a more realistic variant: `Employee` base with `CalculateOvertime()` and a `Contractor` subtype that throws because contractors don't have overtime. Student redesigns the hierarchy. Pattern 1 collapsible solution.
- **Cuando va demasiado lejos** (per D-09): Subtypes that throw `NotImplementedException`. Show it IS a valid signal to redesign, but note that sometimes wrapping with a no-op (logging, null object pattern) is acceptable when the contract explicitly allows it (e.g., `IDisposable.Dispose()` is a no-op for types with nothing to dispose).
- Blockquote: `> **Respuesta de entrevista:** "LSP se viola cuando un subtipo no puede cumplir el contrato del tipo base. La senal clasica es NotImplementedException. La solucion es segregar interfaces o redisenar la jerarquia."`

### Section 4: `## ISP -- Interface Segregation Principle`
- **Aplicacion correcta:** Definition ("Los clientes no deben depender de interfaces que no usan"). Business domain: `IPrinter` split into `IPrint`, `IScan`, `IFax` — but use a more realistic example: `IOrderService` split into `IOrderReader` and `IOrderWriter` for a read-only dashboard vs admin panel.
- **Challenge 4** (business domain — inventory per D-05): Given a fat `IInventoryManager` interface with 8 methods, student identifies which clients use which methods and splits into 2-3 focused interfaces. Pattern 1 collapsible solution.
- **Cuando va demasiado lejos** (per D-09): Over-granular interfaces that are ALWAYS consumed together. Show 4 single-method interfaces (`ICanRead`, `ICanWrite`, `ICanDelete`, `ICanUpdate`) that every consumer injects ALL of them — worse than one `ICrudRepository` interface. The cure is worse than the disease.
- Blockquote: `> **Respuesta de entrevista:** "No aplicaria ISP si todos los consumidores siempre usan todos los metodos. Interfaces de un solo metodo que siempre se inyectan juntas crean ceremony sin beneficio — una interfaz cohesiva es preferible."`

### Section 5: `## DIP -- Dependency Inversion Principle`
- **Aplicacion correcta:** Definition ("Los modulos de alto nivel no deben depender de modulos de bajo nivel; ambos deben depender de abstracciones"). Show a `ReportGenerator` depending on `IDataSource` instead of `SqlDatabase` directly. Use primary constructors (C# 12) for concise DI syntax.
- **Challenge 5** (business domain — orders per D-05): Given an `OrderService` that directly instantiates `SqlOrderRepository` and `SmtpEmailSender`, student refactors to inject `IOrderRepository` and `INotificationService` via constructor. Pattern 1 collapsible solution.
- **Cuando va demasiado lejos** (per D-09): DI that complicates small projects. Show a 3-class console utility where adding interfaces + DI container + registrations triples the code for zero testing benefit. Note: in ASP.NET Core the container is free — the overhead is near-zero. But in a standalone script, manual `new` is fine.
- Blockquote: `> **Respuesta de entrevista:** "No aplicaria DIP en proyectos pequenos donde la abstraction no tiene consumidores alternativos y el costo de la indirection supera el beneficio. Cuando el proyecto crece, refactorizar a DI es straightforward."`

### Section 6: `## Resumen: Puntos Clave para la Entrevista` (per Pattern 2)

  7. Como decides el nivel correcto de abstraccion?
