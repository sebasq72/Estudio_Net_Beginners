**Section 1: `## Clean Code: Nombres Descriptivos`** (~15 min)
- Theory: Why naming matters (code is read 10x more than written), Microsoft C# naming conventions (PascalCase for public, camelCase for private/local, _camelCase for fields), meaningful names reveal intent.
- Before/After pattern (from RESEARCH.md lines 278-323 and PATTERNS.md lines 174-194):
  - BEFORE: `class Proc` with `Calc(List<Item> items, string t)` — cryptic names, magic strings
  - AFTER: `class OrderCalculator` with `CalculateTotal(List<OrderItem> items, ShippingRegion region)` — intent-revealing names, enum instead of magic string
- Challenge 1 (business domain per D-05): "Renombra para revelar intencion" — give a class with methods like `DoStuff()`, `Handle()`, `ProcessData()`, `mgr`, `temp`, `x` in an employee scheduling context. Student renames everything. Pattern 1 collapsible solution.

**Section 2: `## Clean Code: Metodos Pequenos y Guard Clauses`** (~15 min)
- Theory: Methods should do ONE thing. Long methods = SRP violation at method level. Guard clauses eliminate nesting (early return). Pragmatic note (per Pitfall 4): "prefer small methods" does NOT mean every method must be 5 lines — extract when it improves readability, not mechanically.
- Before/After: A 40-line method with 4 levels of nesting (null checks inside if/else inside loop). Show the AFTER with guard clauses (early returns at the top) and extracted helper methods.
- Challenge 2 (abstract/technical per D-05 mix): "Refactoriza este metodo" — a `ProcessOrder()` method with 30+ lines that validates, calculates, applies discount, logs, and sends notification. Student extracts to 3-4 small methods. Pattern 1 collapsible solution.

**Section 3: `## Clean Code: DRY (Don't Repeat Yourself)`** (~10 min)
- Theory: Duplication = maintenance burden. BUT: wrong abstraction is worse than duplication (AHA — Avoid Hasty Abstractions). DRY applies to KNOWLEDGE, not just code that looks similar. Two methods that look alike but represent different business rules should NOT be merged.
- Code model: Show two discount calculation methods that look identical NOW but serve different business purposes (seasonal vs loyalty) — explain why merging them would be premature abstraction. Then show a genuine DRY violation: the same tax calculation copy-pasted in 3 places.
- No standalone challenge — this concept integrates into Challenge 3 (integrador).

**Section 4: `## Decision Tree: Clase Abstracta vs Interfaz`** (~15 min, per D-11 and D-12)
- Present the decision tree as a Markdown TABLE (per D-12) with 4 rows:

| Pregunta | Si | No |
|----------|----|----|
| Necesitas compartir estado (fields) entre clases derivadas? | **Abstract class** | Siguiente pregunta |
| Las clases necesitan heredar de otra clase base? | **Interface** (C# no tiene herencia multiple) | Siguiente pregunta |
| Necesitas que tipos no relacionados implementen el contrato? | **Interface** | Siguiente pregunta |
| Necesitas proveer implementacion comun que las derivadas pueden override? | **Abstract class** (o interface con default method si no hay estado) | **Interface** pura |

- After the table, add 2-3 bullet points explaining the most common real-world scenarios:
  - "En la practica, la mayoria de las veces usaras interfaces para contratos y DI"
  - "Abstract classes brillan cuando hay estado compartido + logica parcial (Template Method)"
  - "Desde C# 8, la linea se difumina — ve la siguiente seccion"

- Challenge 3 (refactoring challenge per D-11): Given code that uses `abstract class IPaymentGateway` with no shared state and no shared implementation — just abstract methods. Student identifies it should be an `interface` and refactors, justifying with the decision tree. ALSO give a second mini-scenario where an interface is used but all implementations duplicate the same 5-line validation logic — student identifies this should be an abstract class with that shared logic. Pattern 1 collapsible solution.

**Section 5: `## C# 8 Default Interface Implementations`** (~10 min, per D-11 "nota")
- NOT a full section with challenge — an awareness note (per D-11: "nota sobre C# 8 default implementations").
- Explain what default interface methods (DIMs) are: implementations in interfaces since C# 8.
- Use the `INotificationChannel` example from RESEARCH.md (lines 328-354) showing `SendUrgent` default method.
- **Clearly state limitations (per Pitfall 3 — do NOT overstate):**
  1. DIMs CANNOT have fields (no instance state)
  2. DIMs CANNOT access instance state of the implementing class
  3. DIMs are ONLY accessible via the interface reference, NOT the class reference directly
- Show the access pattern: `email.SendUrgent("test")` = COMPILE ERROR vs `((INotificationChannel)email).SendUrgent("test")` = OK
- Blockquote: `> **Nota importante:** Default interface methods NO hacen obsoletas a las abstract classes. Si necesitas estado compartido (fields), abstract class sigue siendo la unica opcion. DIMs son utiles para evolucionar interfaces sin breaking changes en librerias.`

**Section 6: `## Challenge Integrador: Refactoring Completo`** (~20 min)

  - Uses `abstract class IExporter` where an interface would be better

- Student must: rename, extract methods, apply DRY, convert abstract class to interface, and inject the data dependency.
- Pattern 1 collapsible solution with comprehensive "Puntos clave" (4-5 bullets covering each fix).
